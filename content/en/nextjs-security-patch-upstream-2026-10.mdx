On October 14, the Next.js team shipped the out-of-band security update it had announced six days earlier. It landed in versions **16.4.1** (active LTS) and **15.5.28** (maintenance) and fixes three vulnerabilities: two critical and one high severity. Two of them had already been identified in September, but the fix was held back to give time to coordinate disclosure with the maintainers of the libraries involved.

According to the notice, every version of the 16 line up to 16.4.0 is affected. If you're on 16.3.8 or anything earlier, you need to move to 16.4.1.

*Updated on October 19, after the official notice with the patched versions was published.*

## The three vulnerabilities

According to the official notice and the summaries published about it, they are:

* **Critical, unauthenticated remote code execution in `"use cache"` functions that return typed arrays.** Identifier GHSA-673q-mjm6-r5xr. Affects versions 16.0.0 through 16.4.0.
* **Critical, remote code execution through the Image Optimization API when processing SVGs on glibc-based Linux.** Identifiers CVE-2026-96889 and GHSA-2464-fhr4-w9xw. The root cause is in an upstream image library. Until you update, a workaround is to use sharp 0.35.5 or later.
* **High, denial of service through Server Actions in App Router apps.** Identifier GHSA-p3m5-59mp-jv5r. This one is also fixed on the 15 line, in version 15.5.28.

The affected version ranges differ from one vulnerability to the next. Before deciding how urgent this is for your project, read each advisory on GitHub to see whether your setup, such as using `"use cache"` or images, is in scope.

## Recent timeline

* **September 22:** out-of-band release with versions 16.3.6 and 15.5.26, fixing a critical remote code execution issue in `next/og`. According to Estont's analysis, the 15.x line was not affected by that issue.
* **September 30:** versions 16.3.8 and 15.5.27. The official notice lists seven vulnerabilities: one high, five medium, and one low. Some third-party sources count nine, including one critical.
* **October 8:** Next.js announces the October 14 out-of-band update.
* **October 14:** 16.4.1 and 15.5.28 are released.
* **October 21:** Next.js 15 reaches end of life.

## What upstream vulnerabilities are

An upstream vulnerability isn't in the framework's own code. It lives in a library Next.js relies on underneath, such as image processing. The fix has to land in that library first and only then reach Next.js. That's why two of the fixes were held back after September, and why the date didn't follow the usual schedule.

## Images: who is most exposed

Among the September fixes, one high-severity issue is an SSRF in Image Optimization, tracked as CVE-2026-94483. According to Netlify and daily.dev, it only affects apps that have `images.remotePatterns` configured.

The October issue in the Image Optimization API is a different one, and involves SVG processing. If your app uses `next/image` or the image optimizer, treat this update as a priority.

The September cache poisoning issue in SSG and ISR pages affects self-hosted Pages Router apps. According to Netlify, apps hosted on Vercel are not affected by it.

## What the Next.js 15 end of life changes

Next.js 15 reaches end of life on October 21, 2026. Until then, the line only gets critical and security fixes, no new features. After that date there's no guarantee of new patches. Any fix for an unsupported version would be a case-by-case decision by the team.

In practice, 15.5.28 is likely one of the last versions of the 15 line. If your project is on a version older than 15.5, the recommendation is to migrate to the 16 line. According to endoflife.date, 16.4.0 was released on October 6.

## What to do in your project

**1. Check the installed version**

```bash
npm list next
```

**2. Record the current version before changing anything**

Create a branch and note the version running in production. If something breaks, rolling back is one command.

```bash
git checkout -b nextjs-security-update
```

**3. Update to the patched version for your line**

```bash
# 16 line (active LTS)
npm install next@16.4.1 eslint-config-next@16.4.1

# 15 line (maintenance until 10/21)
npm install next@15.5.28 eslint-config-next@15.5.28
```

Keep `eslint-config-next` on the same version as `next`. If you deploy on Netlify, also update the `@netlify/plugin-nextjs` adapter. Netlify recommends version 5.16.1 or later.

A Releasebot summary suggests a 16.4.2 may exist. I couldn't confirm that version or its advisories, so check the [releases page](https://github.com/vercel/next.js/releases) before pinning a version in your project.

**4. Update the lockfile and build**

```bash
rm -rf .next
npm install
npm run build
```

Don't delete `package-lock.json`. It makes sure everyone on the team, and your deploy pipeline, installs the same versions. `npm install` updates the lock with the new versions. Changing only `package.json` isn't enough: the lock has to be committed too.

Some teams configure their package manager to install only versions that are at least a day old. That's a local setting, not a Next.js rule, but it can delay the 16.4.1 install in a project that uses that kind of gate.

**5. Test before shipping to production**

In staging, go through the most exposed areas:

* Routes using `next/image` and the `/api/og` route, if you use them;
* `"use cache"` functions and Server Actions;
* Middleware and routes behind authentication;
* Sensitive flows such as login and checkout, if you have them.

**6. Deploy and confirm the version in production**

After deploying, confirm that the new build is the one actually serving traffic. A deploy that didn't publish, or a stale cache, can leave a vulnerable version live even though the code is updated.
