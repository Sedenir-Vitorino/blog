On October 8, the Next.js team announced a security update outside the usual schedule, set for October 14. It fixes three vulnerabilities in third-party dependencies: two critical and one high severity. Two of them had already been identified in September, but the fix was held back to give time to coordinate disclosure with the maintainers of those libraries.

If you run a Next.js project in production, it's worth checking today.

<Summary title="Quick summary">
Out-of-band security patch with three upstream vulnerabilities (two critical, one high) scheduled for 10/14. Next.js 15 reaches end of life on 10/21. Update to the patch version for your line and test sensitive routes before shipping to production.
</Summary>

## What upstream vulnerabilities are

An upstream vulnerability isn't in the framework's own code. It lives in a library Next.js relies on underneath, such as image processing, HTTP parsers, or cache and proxy components. The fix has to land in that library first and only then reach Next.js. That's why the announcement mentioned coordinating with the original authors, and why the date wasn't the usual one.

When I wrote this, the official notice didn't list the affected packages or the vulnerability identifiers. If you see library names or CVE numbers elsewhere, check them against the official notice before relying on them.

## What the Next.js 15 end of life changes

Next.js 15 reaches end of life on October 21, 2026. Until then, the line only gets critical and security fixes, no new features. After that date there's no guarantee of new patches. Any fix for an unsupported version would be a case-by-case decision by the team.

In practice, today's patch is likely one of the last for the 15 line. If your project is on a version older than 15.5, the recommendation is to migrate to the 16 line, which is the active LTS.

## What to do in your project

**1. Check the installed version**

```bash
npm list next
```

**2. Update to the patch version for your line**

I couldn't confirm the exact patched version numbers from official notices, so don't copy versions from third-party posts. When the advisory is out, use the version it lists. Until then, the general commands look like this:

```bash
# 16 line (active LTS)
npm install next@latest eslint-config-next@latest

# 15.5 line (maintenance until 10/21)
npm install next@^15.5 eslint-config-next@^15.5
```

Keep `eslint-config-next` on the same version as `next`.

**3. Rebuild without deleting the lockfile**

```bash
rm -rf .next
npm install
npm run build
```

Don't delete `package-lock.json`. It makes sure everyone on the team, and your deploy pipeline, installs the same versions. `npm install` updates the lock with the new versions.

**4. Test before shipping to production**

In staging, go through the routes that depend most on the affected areas:

* Routes using `next/image` and the `/api/og` route, if you use them;
* Server Actions and Server Functions;
* Middleware and routes behind authentication.
