No dia 14 de outubro, o time do Next.js publicou a atualização de segurança fora do calendário que tinha anunciado seis dias antes. Ela chegou nas versões **16.4.1** (LTS ativa) e **15.5.28** (manutenção) e corrige três vulnerabilidades: duas críticas e uma de severidade alta. Duas delas já tinham sido identificadas em setembro, mas a correção ficou para depois para dar tempo de coordenar a divulgação com os mantenedores das bibliotecas envolvidas.

Segundo o aviso, todas as versões da linha 16 até a 16.4.0 são afetadas. Quem está na 16.3.8 ou em qualquer versão anterior precisa subir para a 16.4.1.

<Summary title="Em resumo">
Versões corrigidas: 16.4.1 (linha 16) e 15.5.28 (linha 15). Três falhas: duas críticas (execução remota de código) e uma alta (negação de serviço). Next.js 15 chega ao fim de vida em 21/10. Atualize, faça o deploy e confirme a versão que está rodando em produção.
</Summary>

*Texto atualizado em 19 de outubro, depois da publicação do aviso oficial com as versões corrigidas.*

## As três falhas

Segundo o aviso oficial e os resumos publicados sobre ele, as vulnerabilidades são estas:

* **Crítica, execução remota de código sem autenticação em funções `"use cache"` que retornam typed arrays.** Identificador GHSA-673q-mjm6-r5xr. Afeta as versões de 16.0.0 até 16.4.0.
* **Crítica, execução remota de código pela Image Optimization API ao processar SVGs, em Linux baseado em glibc.** Identificadores CVE-2026-96889 e GHSA-2464-fhr4-w9xw. A origem está em uma biblioteca de imagem upstream. Uma alternativa até atualizar é usar o sharp na versão 0.35.5 ou superior.
* **Alta, negação de serviço via Server Actions em apps com App Router.** Identificador GHSA-p3m5-59mp-jv5r. Esta também foi corrigida na linha 15, na versão 15.5.28.

As faixas de versões afetadas variam de uma falha para outra. Antes de decidir a urgência no seu projeto, leia cada aviso no GitHub para ver se a sua configuração, como o uso de `"use cache"` ou de imagens, está no escopo.

## Linha do tempo recente

* **22 de setembro:** lançamento fora de banda com as versões 16.3.6 e 15.5.26, que corrigiu uma falha crítica de execução remota de código no `next/og`. Segundo a análise da Estont, a linha 15.x não era afetada por essa falha.
* **30 de setembro:** versões 16.3.8 e 15.5.27. O aviso oficial lista sete vulnerabilidades: uma de severidade alta, cinco médias e uma baixa. Algumas fontes de terceiros falam em nove, incluindo uma crítica.
* **8 de outubro:** o Next.js anuncia a atualização fora de banda de 14/10.
* **14 de outubro:** saem a 16.4.1 e a 15.5.28.
* **21 de outubro:** fim de vida da linha 15.

## O que são vulnerabilidades upstream

Uma falha upstream não está no código do próprio framework. Ela está em uma biblioteca que o Next.js usa por baixo, como processamento de imagem. A correção precisa acontecer lá primeiro e só depois chegar ao Next.js. Foi por isso que duas das correções ficaram para depois de setembro, e por isso a data não seguiu o calendário habitual.

## Imagens: quem é mais exposto

Entre as falhas de setembro, uma de severidade alta é um SSRF no Image Optimization, catalogado como CVE-2026-94483. Segundo a Netlify e o daily.dev, ele só afeta aplicações que têm `images.remotePatterns` configurado.

A falha de outubro na Image Optimization API é outra, e envolve o processamento de SVGs. Se o seu app usa `next/image` ou o otimizador de imagens, trate essa atualização com prioridade.

Já a falha de cache poisoning em páginas SSG e ISR, de setembro, afeta quem roda Pages Router self-hosted. Segundo a Netlify, aplicações hospedadas na Vercel não são afetadas por ela.

## O que muda com o fim do Next.js 15

O Next.js 15 entra em fim de vida em 21 de outubro de 2026. Até lá, a linha recebe apenas correções críticas e de segurança, sem novidades. Depois dessa data, não há garantia de novos patches. Qualquer correção para versões sem suporte seria uma decisão caso a caso da equipe.

Na prática, a 15.5.28 deve ser uma das últimas versões da linha 15. Se o seu projeto está numa versão anterior à linha 15.5, a recomendação é migrar para a linha 16. Segundo o endoflife.date, a 16.4.0 saiu em 6 de outubro.

## O que fazer no seu projeto

**1. Descubra a versão instalada**

```bash
npm list next
```

**2. Registre a versão atual antes de mexer**

Crie uma branch e anote a versão que está em produção. Assim, se algo quebrar, o rollback é um comando.

```bash
git checkout -b atualizacao-next-seguranca
```

**3. Atualize para a versão corrigida da sua linha**

```bash
# Linha 16 (LTS ativa)
npm install next@16.4.1 eslint-config-next@16.4.1

# Linha 15 (manutenção até 21/10)
npm install next@15.5.28 eslint-config-next@15.5.28
```

Mantenha o `eslint-config-next` na mesma versão do `next`. Se você hospeda na Netlify, atualize também o adapter `@netlify/plugin-nextjs`. A Netlify recomenda a versão 5.16.1 ou superior.

Um resumo da Releasebot sugere que pode existir uma versão 16.4.2. Não consegui confirmar essa versão nem seus avisos, então confira a [página de releases](https://github.com/vercel/next.js/releases) antes de fixar a versão no projeto.

**4. Atualize o lockfile e faça o build**

```bash
rm -rf .next
npm install
npm run build
```

Não apague o `package-lock.json`. Ele garante que todo o time e o pipeline de deploy instalem as mesmas versões. O `npm install` atualiza o lock com as novas versões. Só o `package.json` alterado não basta: o lock também precisa ir para o repositório.

Alguns times configuram o gerenciador de pacotes para só instalar versões com pelo menos um dia de publicação. Isso é uma configuração local, não uma regra do Next.js, mas pode atrasar a instalação da 16.4.1 em um projeto que usa esse tipo de trava.

**5. Teste antes de subir para produção**

Em staging, passe pelas áreas mais expostas:

* Rotas com `next/image` e a rota `/api/og`, se você usa;
* Funções com `"use cache"` e Server Actions;
* Middleware e rotas protegidas por autenticação;
* Fluxos sensíveis, como login e checkout, se existirem.

**6. Faça o deploy e confirme a versão em produção**

Depois do deploy, confirme que o artefato novo é o que está rodando. Um deploy que não foi publicado, ou um cache antigo, pode deixar a versão vulnerável no ar mesmo com o código atualizado.
